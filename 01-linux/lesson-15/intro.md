# 15. Пользователи, группы, UID, GID и процессы с разными правами

Имя пользователя — удобная метка. Linux принимает решения о доступе в первую очередь по числовым идентификаторам и набору полномочий процесса.

## Как пользователь представлен в системе

У учётной записи есть UID, основной GID, домашняя директория, shell и другие свойства. `id` показывает данные текущих credentials, `whoami` печатает имя эффективного пользователя, `groups` — группы. `getent passwd name` запрашивает учётную запись через системные механизмы NSS.

~~~bash
id
id -u
id -g
getent passwd root
~~~

NSS может получать пользователей не только из `/etc/passwd`, но и через внешние источники идентификации. Поэтому читать только `/etc/passwd` недостаточно для описания всех учётных записей корпоративного сервера.

## Что находится в /etc/passwd

Традиционный формат содержит семь полей, разделённых двоеточиями: login, marker пароля, UID, GID, описание, home и login shell. Хэши паролей обычно хранятся отдельно, например в `/etc/shadow`, а не открытым текстом в `/etc/passwd`.

Поле shell не обязательно означает интерактивный терминал: сервисной учётной записи могут задать `/usr/sbin/nologin`.

## Credentials процесса

Процесс имеет реальные, эффективные и сохранённые UID/GID; для проверки прав часто важны эффективные значения и дополнительные группы. Поэтому пользователь, от имени которого ты вошёл, и пользователь, от имени которого запущен конкретный сервис, могут отличаться.

`ps -eo user,pid,comm` покажет владельцев процессов. Системный веб-сервер может работать от отдельной учётной записи, чтобы чтение модели не давало ему доступ к чужим файлам.

## Почему root не означает «любой процесс может всё»

UID 0 исторически связывают с суперпользователем. Linux разделяет многие привилегии на **capabilities**. Механизмы namespaces, seccomp, LSM и ограничения монтирований могут дополнительно сужать возможности процесса. Root внутри контейнера не обязательно обладает возможностями root на хосте.

Это не причина игнорировать риски root: права остаются широкими и ошибка может затронуть доступные ресурсы.

## Для чего нужны группы

Группа может владеть директорией с файлами моделей. Разным пользователям можно дать доступ через группу, не открывая его всем остальным. Важны не только GID на файле, но и фактические группы процесса.

**Не срезай углы:** не заменяй все владельцы файлов на root для устранения ошибки доступа. Сначала выясни, каким UID/GID запущено приложение и какие права нужны ему для конкретного пути.

**Источники:** [credentials(7)](https://man7.org/linux/man-pages/man7/credentials.7.html), [passwd(5)](https://man7.org/linux/man-pages/man5/passwd.5.html), [capabilities(7)](https://man7.org/linux/man-pages/man7/capabilities.7.html).

## Углубление: права проверяются для процесса, а не для имени в приглашении

Когда служба запускается с `User=mlapi`, ядро проверяет разрешения на чтение модели относительно credentials **конкретного процесса**. То, что ты вошёл по SSH как администратор и способен открыть файл, не доказывает возможность чтения пользователем `mlapi`.

Для расследования сравни:

~~~bash
id
ps -eo user,pid,comm | head
stat -c 'owner=%U group=%G mode=%a' /etc/os-release
~~~

Если доступ основан на группе, важна не только основная GID, но и supplementary groups процесса. Добавление пользователя в группу может не немедленно изменить credentials **уже запущенного** процесса: часто нужен новый сеанс либо перезапуск службы.

### Root внутри контейнера

UID 0 внутри namespace может отображаться на другой UID хоста, а набор capabilities ограничиваться контейнерным runtime. Но контейнерная изоляция не даёт права считать root безопасным: с доступными файловыми монтированиями, устройствами и сокетами процесс по-прежнему может причинить ущерб. В Docker-модуле мы проверим это на примере non-root USER и bind mounts.

### Проверка имени пользователя

`getent passwd mlapi` обращается к системной базе имён. Это важнее, чем поиск по одному локальному `/etc/passwd`, если организация применяет сетевую аутентификацию.
