# 10. Поиск содержимого файлов: grep и регулярные выражения

Когда inference-сервис упал, в журнале могут быть сотни тысяч строк. `grep` не «понимает ошибки Python»; он выбирает строки по текстовому шаблону. Правильно составленный запрос быстро сужает область поиска, неправильно составленный скрывает нужный traceback или даёт массу ложных совпадений.

## Что именно сравнивает grep

~~~bash
grep ERROR app.log
~~~

`grep` читает строки файла и печатает те, которые соответствуют шаблону `ERROR`. По умолчанию это **basic regular expression**, а не обязательно буквальная строка. Для буквального поиска существует `grep -F`.

~~~bash
printf 'model.pt\nmodelXpt\n' > /tmp/grep-test.txt
grep 'model.pt' /tmp/grep-test.txt
grep -F 'model.pt' /tmp/grep-test.txt
~~~

В первом `grep` точка означает любой одиночный символ. Во втором точка — буквальная. Эта разница важна, когда ищешь имя файла или номер версии.

## Часто используемые опции

`-n` показывает номер строки, `-i` игнорирует регистр, `-v` выбирает строки без совпадения, `-c` считает соответствующие строки. `-A 3` включает три строки после совпадения, `-B 3` — три до, `-C 3` — контекст с обеих сторон.

В stack trace полезно получить контекст: строка `ERROR` сама по себе не раскрывает причину, а следующая за ней строка исключения может раскрывать.

## Базовый и расширенный regex

`grep -E 'ERROR|WARN' app.log` использует extended regex. Символ `|` здесь означает альтернативу **внутри regex**, а не shell pipe: одинарные кавычки защищают его от разбора Bash. Без кавычек shell попытался бы построить pipeline из разных команд.

`^` обозначает начало строки, `$` — конец, `[0-9]` — диапазон символов, `.*` — любую последовательность. Напомним: Bash glob `*.log` и regex `.*\.log$` — совершенно разные языки.

## Коды выхода

`grep` обычно возвращает 0 при совпадении, 1 если совпадений нет, 2 при ошибке. Это не значит, что отсутствие совпадений всегда неисправность сервиса. Скрипт должен трактовать результат с учётом своей задачи.

~~~bash
grep -Fq 'READY' app.log
echo $?
~~~

`-q` подавляет обычный вывод, сохраняя статус проверки. В Bash это удобно внутри `if`.

## Pipe или чтение файла напрямую

`cat app.log | grep ERROR` работает, но `grep ERROR app.log` короче и запускает меньше процессов. Pipe полезен, когда результат одного фильтра нужен другому:

~~~bash
grep -E 'ERROR|WARN' app.log | wc -l
~~~

Здесь `grep` выбирает строки, `wc` считает их. Но статус всей цепочки требует отдельного внимания — изучим `pipefail`.

## Практический эксперимент

Создай файл с сообщениями `INFO`, `WARN`, `ERROR`. Сравни число строк у `grep -F 'ERROR'` и `grep -E 'WARN|ERROR'`. Затем проверь `grep -n -C 1 ERROR file`, чтобы увидеть контекст. Не читай готовую команду, пока не исследуешь флаги `-n` и `-C` через `grep --help`.

**Не срезай углы:** регулярное выражение нужно проверить на положительных и отрицательных примерах. Фильтр, который находит `model.pt` и случайно `modelXpt`, ещё не готов.
