# Урок 10. Поиск текста: grep, строки логов, regex и коды выхода

**Ориентир:** 55–80 минут. Лабораторная открывает новую временную Ubuntu VM. Не изменяй ничего за пределами указанных тестовых путей.

## Почему grep постоянно нужен инженеру

В логах PyTorch или сервиса ты часто ищешь не файл, а **строки**, соответствующие условию. `grep error events.log` печатает строки с подстрокой `error`, `grep -n` добавляет номера строк, `grep -i` игнорирует регистр, `grep -v` выбирает НЕподходящие строки. Наличие совпадений отражается и в коде завершения: обычно `0` — нашёл, `1` — не нашёл, `2` — ошибка.

## Фиксированная строка и регулярное выражение

`grep -F 'model.pt' file` ищет буквальный текст с точкой. Обычный `grep 'model.pt'` интерпретирует `.` как любой символ в базовом regex. `grep -E 'ERROR|WARN' file` использует расширенный синтаксис regex. Не смешивай regex с glob-масками вида `*.log`: там другой синтаксис.

## Данные через stdin

`cat events.log | grep ERROR` работает, но `grep ERROR events.log` короче и избегает лишнего процесса. Pipe становится действительно полезен, когда нужно соединить два преобразования, например `grep -E 'ERROR|WARN' file | wc -l`. Это хороший пример Unix-подхода: небольшие программы выполняют понятные операции.

## Контекст события

`grep -A 3 pattern file` даёт три строки после совпадения, `-B` — до, `-C` — по обе стороны. Иногда именно соседние строки содержат traceback или сообщение, которое раскрывает причину инцидента. Нельзя диагностировать сервис по одной строке `ERROR`, игнорируя её контекст.

**Не срезай углы:** попробуй сначала найти совпадение вручную и только потом построить фильтр. Проверяй, что regex не ловит лишние строки.

**Документация:** [GNU grep](https://www.gnu.org/software/grep/manual/grep.html).
