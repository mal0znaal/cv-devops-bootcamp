# 20. /proc/PID: взгляд на процесс через интерфейс ядра

После запуска Python Linux создаёт для процесса ряд доступных через procfs представлений. Они позволяют без отладчика узнать PID, состояние, аргументы, текущую директорию, открытые файлы и часть метаданных.

## Что находится в /proc/PID

`/proc/PID/status` содержит состояние процесса, UID/GID, память и прочие поля. `/proc/PID/cmdline` обычно содержит аргументы, разделённые нулевыми байтами. `/proc/PID/environ` хранит переменные окружения в сходной форме. Последний файл способен раскрыть токены и пароли — его нельзя публиковать как «безобидный лог».

~~~bash
echo $$
cat /proc/$$/status | head -n 25
ps -p $$ -o pid,ppid,stat,comm
~~~

Символы `$$` раскрывает Bash, подставляя PID текущей оболочки в соответствующем контексте.

В команде `ls -l /proc/$/fd/{0,1,2}` фигурная запись `{0,1,2}` — **brace expansion** Bash. Оболочка создаёт из неё три пути — `/proc/PID/fd/0`, `/proc/PID/fd/1`, `/proc/PID/fd/2` — и передаёт их программе `ls`. PID при этом берётся из `$`. Можно написать и три отдельных аргумента: результат будет тем же.

## Дескрипторы процесса

`/proc/PID/fd` содержит ссылки на открытые файловые дескрипторы. Номера 0, 1, 2 обычно обозначают stdin/stdout/stderr, но сами объекты могут быть терминалом, pipe или файлом. Другие номера используются для сокетов, логов, файлов модели и т.д.

~~~bash
ls -l /proc/$$/fd
~~~

Это связывает тему стандартных потоков с настоящими объектами ядра.

## Удалённый, но всё ещё открытый лог

Когда процесс держит открытый дескриптор файла, удаление имени через `rm` не обязано сразу освободить занимаемые блоки. Процесс продолжает писать в открытый файловый объект до закрытия дескриптора. Поэтому `df` и `du` порой показывают противоречащие на первый взгляд сведения.

## Состояния процесса

Поле State в `status` сообщает, runnable ли задача, спит ли она, остановлена или уже стала zombie. Разовое значение не объясняет производительность: нужно наблюдать динамику и причины ожидания.

## Ограничения видимости

В контейнере PID namespace может показывать только часть процессов. Политика `hidepid` и права могут ограничивать чтение файлов чужих PID. Даже root внутри контейнера не обязательно видит процессы хоста.

**Не срезай углы:** не читай `/proc/*/environ` массово и не отправляй вывод в публичный чат. Для диагностики выбирай нужные безопасные поля.

**Источники:** [proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html), [proc_pid_fd(5)](https://man7.org/linux/man-pages/man5/proc_pid_fd.5.html).

## Эксперимент: увидеть дескриптор файла

Открой в одном терминале небольшой Python-процесс, который удерживает файл открытым и некоторое время ожидает. Сравни список `/proc/PID/fd` до и после открытия. Ты обнаружишь дополнительный дескриптор, обычно номер больше 2. Связь дескриптора и имени файла — две разные сущности: имя можно удалить, но уже открытый объект остаётся.

### Почему cmdline отделён нулевыми байтами

Аргументы системного интерфейса `execve` — список строк. Если просто соединить их пробелами, не удастся отличить один аргумент `'my model.pt'` от двух `my` и `model.pt`. Интерфейс `/proc/PID/cmdline` разделяет аргументы NUL, позволяя сохранить границы. Для просмотра человекочитаемого представления используют `ps -p PID -o args=`, но оно не всегда позволяет восстановить исходный `argv` без неоднозначности.

### Проверка окружения

Не выводи всё `/proc/PID/environ` в публичный терминал или лог: сервис может хранить там токены. При разрешённом доступе безопаснее проверять точечный диагностический параметр в контролируемом окружении, например собственной учебной программы.
