# 01. Из чего состоит Linux и что делает ядро

Ты запускаешь Python-скрипт с YOLO. Скрипт читает веса модели с SSD, загружает изображения, передаёт тензоры в PyTorch, использует GPU и открывает HTTP-порт для запросов. В Python-коде нет ни реализации драйвера SSD, ни планировщика процессов, ни сетевого стека TCP. Эту работу разделяют библиотеки, драйверы и операционная система. Чтобы понимать ошибки таких приложений, стоит разобрать, кто отвечает за каждое действие.


**Ориентир для первого чтения:** разберись, какие задачи решают ядро и пользовательские программы, как файл читается через системный вызов и почему процесс не может напрямую обращаться к произвольной памяти. Подробности про DMA, TLB, ABI и cgroups остаются в тексте как второй уровень — к ним можно возвращаться при изучении последующих тем. Сокращения объясняются в соответствующих разделах.

На бесплатном Killercoda время терминала ограничено одним часом. Эту длинную главу удобно сначала читать в GitHub, а упражнения выполнить уже в запущенной VM.

## 1. Компьютер до запуска операционной системы

У компьютера есть процессор, оперативная память, устройства хранения, сетевые адаптеры, контроллеры USB, видеокарта. Процессор выполняет машинные инструкции. Сам по себе он не знает, какой процесс «должен получить» CPU следующим, кому принадлежит файл и разрешено ли программе открыть сетевой порт. Это правила, которые устанавливает программное обеспечение.

Когда одновременно запущены браузер, Python, Docker и SSH-сервер, каждому процессу требуется память и процессорное время. Нескольким программам нужен доступ к одному диску. Нужно предотвратить ситуацию, при которой ошибочная запись одного приложения повреждает память другого. Операционная система управляет этими общими ресурсами.

На современных CPU есть разные уровни привилегий исполнения. Пользовательский код и код ядра работают с разными возможностями доступа к памяти и инструкциям процессора. Ядро использует эти аппаратные механизмы для изоляции процессов. Граница не абсолютна в философском смысле — уязвимости в ядре существуют, — но без неё обычный текстовый редактор получил бы возможность записывать произвольные данные в память любой программы.

## 2. Что такое ядро Linux

**Linux** в строгом техническом смысле — ядро операционной системы. Оно постоянно находится в памяти работающей системы, управляет процессами, виртуальной памятью, устройствами, файловыми системами и сетевыми соединениями. Ядро состоит из множества подсистем, которые взаимодействуют друг с другом.

Его удобно рассматривать через пять задач:

1. **Выполнение процессов.** Ядро создаёт процессы и потоки, переключает CPU между ними, обрабатывает сигналы и ведёт учёт потребления ресурсов.
2. **Работа с памятью.** Оно создаёт для процессов виртуальные адресные пространства, отображает страницы на физическую память, управляет page cache и реагирует на нехватку RAM.
3. **Ввод-вывод и файловые системы.** Оно обслуживает системные вызовы чтения и записи, проверяет разрешения, использует драйверы и файловые системы.
4. **Сетевой стек.** Оно реализует значительную часть TCP/IP, маршрутизации, сокетов и обработки входящих сетевых пакетов.
5. **Доступ к устройствам.** Драйверы ядра взаимодействуют с контроллерами и оборудованием, предоставляя программам устойчивые интерфейсы.

Linux — **монолитное ядро с поддержкой загружаемых модулей**. Монолитность здесь означает, что его основные подсистемы и драйверы могут работать в общем привилегированном адресном пространстве ядра. Это не значит, что всё ядро собрано в один неделимый исполняемый файл: некоторые компоненты загружаются как модули. Команда `lsmod` показывает загруженные модули, а `modinfo` выводит сведения о конкретном модуле. Наличие модуля зависит от конфигурации конкретной машины.

### Эксперимент: какое ядро запущено

~~~bash
uname -s
uname -r
uname -m
cat /proc/version
~~~

`uname -s` сообщает имя ядра, `uname -r` — его release, `uname -m` — архитектуру машины. Это разные характеристики. Строка `6.x.y-...` — не номер Ubuntu, а идентификатор сборки ядра. `/proc/version` предоставляется ядром через procfs; обычный `cat` читает эти данные как файл, хотя текст создаётся ядром при обращении.

## 3. Терминал, shell и команда — три разных объекта

Когда ты печатаешь `pwd` в браузерном терминале Killercoda, происходят несколько событий. Интерфейс браузера передаёт ввод терминальной сессии. Внутри машины работает shell, обычно Bash. Bash разбирает ввод, определяет встроенную команду либо ищет внешнюю программу и запускает её. Вывод возвращается обратно в терминал.

**Терминал** отвечает за взаимодействие с человеком. **Shell** — интерпретатор команд и небольшой язык программирования. **Утилиты** — отдельные программы, которые shell запускает. **Ядро** управляет процессами и вводом-выводом. Одна строка команды проходит через несколько уровней, но каждую часть выполняет конкретный компонент.

Почему `cd` обычно встроена в shell? Если бы отдельный дочерний процесс поменял свою рабочую директорию и завершился, директория родительского Bash осталась бы прежней. Bash должен изменить **собственное состояние**, поэтому `cd` реализована как builtin. Сравни:

~~~bash
type cd
type ls
pwd
cd /tmp
pwd
~~~

### Как работать с самым первым терминалом

Терминал Killercoda — окно, в которое вводятся команды. После набора строки нажимай Enter. Следующий символ приглашения означает, что shell готов принимать новую команду. Если видишь длинный вывод, это ещё не ошибка: отличай текст, напечатанный программой, от приглашения.

У символов есть значения, которые мы подробнее исследуем в следующих уроках. Пока нужны четыре:

- `/` начинает абсолютный путь, например `/etc/os-release`.
- `~` означает домашний каталог текущего пользователя (это сокращение разворачивает Bash).
- `mkdir` создаёт каталог. В `mkdir -p ~/lab01` опция `-p` заставляет создать отсутствующие каталоги по пути; если папка уже есть, повторная команда не падает только из-за её существования.
- `cat файл` печатает содержимое файла. `nano файл` открывает простой терминальный текстовый редактор.

Создать текстовый файл можно без знания перенаправлений: выполни `mkdir -p ~/lab01`, потом `nano ~/lab01/kernel.txt`. В редакторе набери одну строку, нажми **Ctrl+O** для сохранения, **Enter** для подтверждения имени и **Ctrl+X** для выхода. Проверь результат через `cat ~/lab01/kernel.txt`. Символы `>`, `>>` и `|` мы изучим отдельно; сейчас они не нужны.

Команды `uname` и `ps` в этой лекции используются для наблюдения, а не изменения системы. `uname -r` печатает версию запущенного ядра, `ps -p 1 -o comm=` — имя видимого процесса с PID 1. Здесь `-r` и `-p` — опции **разных программ**, и смысл каждой определяется справкой конкретной программы.


## 4. User space и kernel space

Твоё Python-приложение работает в **user space** — пользовательском пространстве. Его инструкции выполняются без права произвольно менять память ядра или программировать аппаратные устройства. Ядро работает в **kernel space** с более высокими привилегиями.

Представь вызов:

~~~python
with open("/tmp/weights.bin", "rb") as f:
    data = f.read(4096)
~~~

Python вызывает собственные реализации файлового ввода-вывода, которые в конечном счёте обращаются к функциям системной библиотеки и системным вызовам, таким как `openat` и `read`. В момент системного вызова процессор переходит в режим ядра. Ядро проверяет существование пути, разрешения и параметры открытия, находит файловый объект через VFS, а затем обеспечивает чтение нужных данных — из кэша либо с накопителя.

Здесь есть две разные границы:

- **API языка и библиотек**: `open()` в Python — удобный интерфейс Python. Это не непосредственная инструкция процессора.
- **Системный вызов (syscall)**: контролируемый способ попросить ядро выполнить операцию. Например, `read(2)` — системный вызов чтения.

Число в `read(2)` означает раздел 2 справочника `man`, а не «вторая версия read». В разделе 2 находятся системные вызовы. У системных вызовов есть номера и соглашения о передаче аргументов, зависящие от архитектуры и ABI.

**Полезный опыт:** `strace` показывает системные вызовы процесса. Если программа доступна, попробуй на учебной VM:

~~~bash
strace -e trace=openat,read,close cat /etc/os-release
~~~

Ты увидишь, что простое чтение файла предполагает несколько вызовов ядра. Если `strace` не установлен, не нужно ради первого урока перестраивать машину. Вернись к эксперименту позже.

## 5. Что делает ядро в момент системного вызова

Обсудим конкретный запрос: Python хочет прочитать первые 4096 байт файла модели. В коде написано `f.read(4096)`, но во время исполнения участвуют несколько уровней. Метод объекта файла в Python в конечном счёте использует системные интерфейсы чтения. Для обычного файла одна из операций выполняется через системный вызов `read`.

В user space программа вызывает библиотечную функцию, которая готовит номер системного вызова и аргументы в соответствии с **соглашением о вызовах** конкретной архитектуры. На x86-64 переход в ядро выполняется с помощью специальной процессорной инструкции. Ядро принимает управление через входную точку системных вызовов, проверяет аргументы и находит реализацию запрошенной операции.

Параметр чтения содержит номер файлового дескриптора, адрес буфера пользовательской программы и количество байтов. Ядро обязано проверять, что доступ к пользовательскому буферу допустим: пользовательский указатель сам по себе не предоставляет право читать или писать произвольную память ядра.

После чтения ядро возвращает результат: например, число прочитанных байтов. Значение меньше запрошенного количества не обязательно ошибка — EOF, прерывания или особенности источника данных могут привести к частичному чтению. При ошибке системный интерфейс сообщает соответствующий код; библиотечная обёртка обычно превращает его в привычный API с errno или исключением на уровне языка.

Обрати внимание на разницу: **режим ядра** — способ выполнения привилегированного кода, а **системный вызов** — контракт между программой и ОС. Один и тот же пользовательский код может обращаться к одному и тому же интерфейсу, даже если конкретное оборудование под ним отличается.

### Почему обычная функция C не равна системному вызову

Функция `strlen` определяет длину строки в памяти текущего процесса; для этого не требуется обращение к ядру на каждый символ. А `openat` должен попросить ядро разрешить путь в файловой системе и предоставить файловый объект. Различие не в языке C или Python, а в том, выполняется ли операция исключительно внутри пользовательского процесса либо требует полномочий ОС.

## 6. Почему процессы изолированы

Предположим, Python-процесс считает матрицу и хранит в ней массив из миллиона элементов. Программа оперирует **виртуальными адресами**. Ядро вместе с аппаратным MMU организует отображение виртуальных страниц в физическую память. Два процесса могут использовать одинаковые численные виртуальные адреса, но они не обязаны указывать на одни и те же физические страницы.

Виртуальная память решает сразу несколько задач. Процесс получает удобное адресное пространство; память разных процессов изолирована; страницы можно отображать на файлы; часть данных хранить в RAM только при необходимости. Когда программа обращается к странице, для которой ещё нет подходящего отображения, процессор может вызвать **page fault**. Ядро выясняет, нужно ли подгрузить страницу, создать её или завершить процесс ошибкой доступа.

Page fault не обязательно означает неисправность. Обычная ленивая загрузка страниц использует page faults как часть нормальной работы. А ошибка `Segmentation fault` возникает при недопустимом обращении, которое не удалось корректно обработать.

### Как это связано с PyTorch

Тензор на CPU занимает системную память, а CUDA-тензор — память, выделенную в GPU по правилам CUDA runtime и драйвера. Из-за этого `free -h` не сообщает, сколько видеопамяти заняла модель. Для GPU понадобятся отдельные инструменты. Но и CPU-тензор не существует «вне Linux»: страницы памяти, адресное пространство и учёт ресурсов по-прежнему обеспечиваются ядром.

## 7. Виртуальная память подробнее: страницы, таблицы и Copy-on-Write

Приложение работает с виртуальными адресами. Аппаратный **MMU** переводит их в физические адреса по правилам таблиц страниц. Процессор кеширует результаты трансляции в **TLB**, чтобы не выполнять полный обход таблиц при каждом обращении к памяти.

Обычно память управляется страницами; часто стандартная страница на x86-64 имеет размер 4 KiB, но система может поддерживать большие и huge pages. Точный размер на текущей машине можно узнать через `getconf PAGESIZE`. Не надо считать 4096 универсальной константой для всех архитектур.

Когда программа просит выделить память, резервирование виртуального адресного пространства и немедленное выделение физических страниц могут происходить в разные моменты. При первом обращении к странице может возникнуть page fault, после которого ядро создаст отображение или загрузит данные.

### Почему fork экономит копирование памяти

При создании дочернего процесса с помощью `fork` современная ОС обычно не копирует немедленно каждую страницу адресного пространства родителя. Используется **Copy-on-Write (CoW)**: страницы некоторое время остаются общими на чтение, а при попытке изменения создаётся независимая копия нужной страницы.

Так запуск дочернего процесса может быть значительно дешевле полного копирования всего объёма памяти. Но у большой программы с обширным адресным пространством остаются накладные расходы, а изменение множества страниц после fork приводит к реальным копированиям.

С этим механизмом ты встретишься в процессных dataloader workers, multiprocessing и некоторых схемах запуска серверов. Он не гарантирует отсутствие роста памяти при работе нескольких процессов.

### Виртуальная память не означает, что вся RAM свободна

`free -h` и `/proc/meminfo` отображают разные категории памяти. Часть занята процессами, часть кэшем, часть ядром. Операционная система пытается эффективно использовать физическую память, поэтому низкое значение `MemFree` само по себе не доказывает проблему. При оценке давления на память важны `MemAvailable`, swap, реальные аллокации, OOM-события и характер нагрузки.

## 8. Почему одновременно работают сотни процессов

У компьютера с восемью логическими CPU могут быть сотни запущенных процессов и потоков. Они не исполняются все одновременно. Ядро выбирает, какой поток получит процессорное время, и переключает CPU между runnable-задачами. Так работает **планировщик (scheduler)**.

Процесс — это выполняющаяся программа с собственными ресурсами и адресным пространством. В одном процессе может быть несколько потоков: они разделяют значительную часть ресурсов и память процесса, но имеют собственное состояние исполнения. В Linux процесс и поток реализуются через родственные механизмы задач; точные подробности рассмотрим в уроке о процессах.

### Эксперимент

~~~bash
ps -e -o pid,ppid,stat,comm | head -n 15
nproc
uptime
~~~

В `ps` ты увидишь PID, PPID, состояние и имя команды. `nproc` показывает число доступных процессоров с точки зрения команды. `uptime` печатает в том числе load average. **Load average не равен проценту загрузки CPU**: в Linux в нём учитываются runnable-задачи и некоторые задачи в непрерываемом ожидании. Это станет существенно позже, когда будем диагностировать перегрузку сервера.

## 9. Планировщик и переключение контекста

У каждого исполняемого потока есть контекст: значения регистров, программный счётчик, состояние стека и информация об адресном пространстве. Когда ядро решает передать CPU другому потоку, оно сохраняет необходимое состояние текущей задачи и восстанавливает контекст следующей. Это **context switch**.

Если поток ждёт поступления данных из сокета, он не обязан занимать CPU активным циклом. Системный вызов может перевести его в состояние ожидания; планировщик отдаст процессор другой runnable-задаче. После появления данных ядро разбудит ожидающую задачу, и она снова будет участвовать в планировании.

Именно поэтому «один процесс запущен» не означает «он прямо сейчас исполняет инструкции». В `ps` процесс может иметь `S` или `D` вместо `R`. Ожидание при чтении файла и вычисление матричного произведения — разные типы нагрузки. При отладке они требуют разных инструментов.

### При чём здесь потоки Python

PyTorch и библиотеки линейной алгебры могут использовать собственные CPU-пулы потоков. При увеличении числа рабочих потоков не всегда происходит линейное ускорение: потоки конкурируют за CPU, кэш-память, пропускную способность памяти и синхронизацию. На машине с ограничением cgroups доступное CPU-время может быть меньше общего числа ядер на хосте.

Поэтому `nproc`, `ps -T`, `top -H` и данные о cgroups дают разные стороны картины. Нужно понимать, какую именно величину показывает инструмент, а не выбирать самое большое число в таблице.

## 10. Что происходит при чтении файла

На пути от `open()` до данных на диске участвуют несколько подсистем.

Сначала программа задаёт путь. Ядро через **VFS (Virtual File System)** работает с единым интерфейсом файлов, каталогов и точек монтирования. Конкретная файловая система — ext4, XFS, tmpfs и т.д. — реализует свои операции в рамках этого интерфейса. Файл не обязан физически лежать на SSD: например, содержимое `/proc/meminfo` создаётся ядром, а файл в `tmpfs` может размещаться в памяти.

При обращении к обычному файлу ядро может найти нужные данные в **page cache**. Тогда не требуется физическое чтение накопителя для каждого `read()`. Если данных нет в кэше, файловая система и блочный слой организуют ввод-вывод через драйвер устройства. Точный путь зависит от файловой системы, режима открытия и доступных аппаратных механизмов.

Этим объясняется, почему первый запуск inference-пайплайна после загрузки машины иногда читает веса медленнее повторного: при повторном чтении часть данных может оказаться в page cache. Это не единственная причина различия во времени; на результат также влияют прогрев CUDA, аллокации, компиляция ядер и другие факторы.

### Эксперимент: виртуальный файл

~~~bash
ls -lh /proc/meminfo
head -n 7 /proc/meminfo
findmnt /proc
~~~

Попробуй ответить: есть ли у `/proc/meminfo` обычная постоянная копия на SSD? Нет, его содержимое экспортирует ядро через procfs. Почему тогда команда `head` умеет его читать? Потому что для пользовательской программы это файловый интерфейс.

## 11. Page cache, буферизация и запись на накопитель

Когда программа читает обычный файл, ядро часто обслуживает запрос из page cache. При записи байтов в файл изменения могут сначала оказаться в памяти как **dirty pages**, а сброс на устройство выполнится позже. Значит, успешный вызов `write` не равен гарантии, что данные уже переживут внезапное отключение питания.

Для специальных требований к сохранности приложения используют системные механизмы `fsync`, `fdatasync` и соответствующие гарантии файловой системы. У них есть накладные расходы. Базы данных и системы хранения моделей должны выбирать политику сохранности осознанно.

### Эксперимент на маленьком файле

~~~bash
printf 'model=v1\n' > /tmp/cache-demo.txt
stat /tmp/cache-demo.txt
cat /tmp/cache-demo.txt
~~~

Ты не увидишь сам page cache напрямую простым `cat`, но можешь различить интерфейсы: файл хранится в файловой системе; `stat` читает метаданные; `cat` получает байты через системные вызовы. Позже по журналу и инструментам наблюдения научимся определять, когда система упирается в накопитель.

### Почему нельзя строить замеры по одному запуску

При сравнении двух вариантов загрузки моделей не перепутай прогрев page cache с преимуществом алгоритма. Для корректного бенчмарка фиксируют размер данных, состояние системы и последовательность повторов. На GPU к этому добавляются прогрев CUDA, синхронизация и возможное кэширование памяти.

## 12. Как работает сеть в Linux

Когда FastAPI начинает слушать порт 8000, приложение создаёт TCP-сокет и вызывает через библиотеки системные интерфейсы вроде `socket`, `bind` и `listen`. Ядро связывает сокет с адресом и портом, принимает входящие сетевые пакеты через сетевой стек, обрабатывает TCP-соединение и предоставляет приложению поток байтов.

HTTP-сервер разбирает уже **HTTP-протокол** на уровне приложения. Ядро не решает, какой JSON должен вернуть endpoint `/predict`. Поэтому сервис может иметь живой процесс и открытый порт, но возвращать HTTP 500. Разницу между сетевой доступностью и работоспособностью приложения ты увидишь в последней миссии модуля.

Для локального опыта не нужен интернет:

~~~bash
ip -br addr
ip route
ss -ltn
~~~

Вывод покажет интерфейсы, маршруты и слушающие TCP-сокеты. Если команда отсутствует, посмотри, как она называется в Ubuntu-пакетах, но пока не меняй системные настройки.

## 13. Прерывания и работа с устройствами

Процессор не должен бесконечно спрашивать накопитель: «ты уже прочитал блок?» Устройства и контроллеры могут уведомлять CPU о событиях через **аппаратные прерывания**. Ядро содержит обработчики событий и механизмы отложенной работы, чтобы быстро реагировать на оборудование и не держать процессор в обработчике дольше необходимого.

Рассмотрим сетевой пакет. Сетевая карта получает кадр и размещает данные в доступных ей буферах. Современные системы широко используют **DMA (Direct Memory Access)**: контроллер способен переносить данные между устройством и памятью без копирования каждого байта отдельной инструкцией CPU. После получения пакета драйвер и сетевой стек ядра обрабатывают соответствующие данные, а приложение получает их через сокет.

Не каждый пакет обязательно означает отдельное аппаратное прерывание. Высокопроизводительные драйверы используют механизмы вроде interrupt moderation и NAPI: часть работы выполняется пакетами с опросом очередей, чтобы избежать чрезмерных затрат CPU на частые прерывания.

Эти детали объясняют, почему сетевой throughput зависит не только от скорости линка. Возможны ограничения CPU на обработку пакетов, число очередей сетевого адаптера, настройки offload и поведение приложения. Для первого модуля не нужно настраивать NAPI, но важно не считать сеть «внешним кабелем, который не имеет отношения к ядру».

### Как наблюдать прерывания безопасно

~~~bash
head -n 15 /proc/interrupts
cat /proc/softirqs | head
~~~

На некоторых виртуальных машинах содержимое этих интерфейсов будет отличаться от физического сервера: виртуализатор предоставляет свои устройства и события. Наблюдаемое отсутствие имени реальной сетевой карты не является ошибкой Linux.

## 14. Драйверы, модули и GPU

Драйвер — программный компонент, работающий с конкретным классом устройств. Для сетевой карты драйвер общается с её контроллером; для NVMe — с интерфейсом накопителя. Не каждый драйвер является отдельно загружаемым модулем: часть функций может быть встроена непосредственно в ядро.

С NVIDIA ситуация сложнее, чем «поставил CUDA в pip». Там есть драйверные компоненты, связанные с ядром и GPU, пользовательские библиотеки NVIDIA, CUDA runtime и фреймворк. В контейнере может быть установлен PyTorch с нужными CUDA-библиотеками, но **контейнер использует ядро хостовой машины** и не приносит с собой собственный работающий драйвер ядра. Поэтому совместимость драйвера хоста и пользовательских библиотек имеет значение.

`nvidia-smi` общается с драйверной инфраструктурой NVIDIA. Если в учебной VM нет GPU и NVIDIA-драйвера, отсутствие команды ожидаемо: это не неисправность Linux.

## 15. Где заканчивается ядро и начинается дистрибутив

Ubuntu — **дистрибутив Linux**. Он включает ядро, системные библиотеки, командные утилиты, пакетный менеджер, службы, средства конфигурации и готовые политики. Debian, Ubuntu, Fedora и Arch могут использовать ядро Linux, но отличаются версиями пакетов, жизненным циклом обновлений, системой упаковки и административными соглашениями.

Команда `ls` — не часть ядра Linux. В Ubuntu она обычно входит в пакет GNU Coreutils. `bash` — отдельная программа. `apt` и `dpkg` — инструменты управления пакетами Debian-семейства. `systemd` — пользовательская система инициализации и управления службами. Их можно обновлять или заменять независимо в пределах совместимости.

### Эксперимент: различить уровни

~~~bash
cat /etc/os-release
uname -r
type -a ls
type -a cd
ps -p 1 -o pid,comm,args
~~~

`/etc/os-release` идентифицирует пользовательское окружение дистрибутива. `uname -r` — ядро. `type` объяснит, откуда Bash берёт конкретную команду. `ps -p 1` покажет первый процесс в видимом пространстве PID. В учебном контейнере PID 1 может быть не systemd — это нормально: контейнер способен иметь собственное PID namespace.

## 16. Как Linux загружается

Во время включения компьютера процессор начинает выполнять **firmware** — встроенное программное обеспечение платы, запускаемое до операционной системы (на современных ПК чаще UEFI, на старых — BIOS). Firmware инициализирует оборудование и передаёт управление загрузчику или загрузочной программе. Загрузчик располагает в памяти ядро и передаёт ему параметры запуска. Затем ядро инициализирует память, драйверы и необходимые подсистемы.

При необходимости используется **initramfs** — временная ранняя корневая файловая система. В ней находятся программы и драйверы, необходимые для обнаружения и монтирования настоящей корневой файловой системы, например при шифровании диска или сложной конфигурации накопителей. После подготовки корня управление переходит к основной системе.

Ядро запускает первый пользовательский процесс; в обычной современной Ubuntu это `systemd` с PID 1. Он запускает системные сервисы, управляет зависимостями между ними, а затем пользователь может войти в систему и получить графическую сессию или SSH-доступ.

Это упрощённая типичная схема, не универсальный сценарий каждой Linux-системы: у встроенных устройств бывает иной загрузчик и init, а в контейнере вообще не происходит полноценной аппаратной загрузки ядра.

Попробуй безопасные команды:

~~~bash
ps -p 1 -o pid,comm,args
cat /proc/cmdline
systemctl get-default
~~~

Если `systemctl` сообщает, что система не загружена с systemd, проверь, где ты выполняешь команды. VM и Docker-контейнер имеют разную модель запуска.

## 17. Почему Docker использует ядро хоста

Виртуальная машина запускает собственное гостевое ядро поверх виртуализированных аппаратных ресурсов. Обычный Linux-контейнер не запускает отдельное ядро Linux. Его процессы работают на ядре хоста, но получают изолированные представления ресурсов через **namespaces**; лимиты CPU и памяти организуются с помощью **cgroups**; файловая система контейнера собирается из монтирований и слоёв образа.

Это объясняет сразу три практических факта.

Во-первых, `uname -r` внутри Ubuntu-контейнера обычно показывает ядро **хоста**, а не «версию ядра Ubuntu из Docker-образа». Во-вторых, контейнер может видеть собственный PID 1, не являющийся процессом PID 1 на хосте. В-третьих, доступ к GPU требует совместной настройки драйвера на хосте, runtime и устройств внутри контейнера.

Сейчас достаточно построить правильную модель. Настраивать namespaces и cgroups будем в Docker-модуле.

## 18. Namespaces и cgroups — основа контейнеров

**Namespaces** меняют представление ресурсов для группы процессов. PID namespace даёт собственную нумерацию процессов; mount namespace — своё дерево монтирований; network namespace — собственные сетевые интерфейсы, сокеты и маршруты; есть также UTS, IPC, user, cgroup и time namespaces. Они изолируют **видимость** и некоторые операции, но не создают отдельное ядро.

**Cgroups** организуют учёт и ограничения ресурсов групп процессов. CPU quota может ограничивать время исполнения, memory controller — потребление памяти, а достижение memory limit может приводить к OOM внутри соответствующей группы. Поэтому процесс в контейнере не обязан иметь доступ ко всей RAM и всем CPU, которые физически существуют на сервере.

Точный формат cgroup зависит от версии (v1/v2) и конфигурации хоста. В современных системах распространена cgroup v2, но её нельзя просто предполагать на каждом сервере.

### Почему установка PyTorch в контейнер не устанавливает драйвер NVIDIA на хост

Контейнерный образ хранит файловую систему пользовательского пространства: программы, библиотеки, Python-пакеты и конфигурацию. Модули ядра и непосредственное управление GPU относятся к хостовой системе. NVIDIA Container Toolkit участвует в предоставлении контейнеру нужных устройств и совместимых пользовательских компонент драйверной инфраструктуры.

Поэтому ошибка несовместимости host driver и CUDA runtime не решается одним `pip install torch`. Чтобы найти первопричину, нужно выяснить версии драйвера, runtime, GPU, доступность устройств и конфигурацию контейнера.

## 19. Что такое Unix и POSIX в этой истории

Linux был создан как Unix-подобная система. Unix — историческое семейство операционных систем и традиция программных интерфейсов. **POSIX** — набор стандартов, описывающих важную часть интерфейсов операционных систем: процессы, файлы, shell и команды. Linux реализует большое количество POSIX-интерфейсов, но содержит и собственные специфичные механизмы: `epoll`, `cgroups`, `namespaces`, множество интерфейсов `/proc` и т.д.

Поэтому команды Bash похожи на команды в macOS, а примеры на чистом POSIX shell нередко переносятся между Unix-системами. Но `systemctl`, `apt` и `nvidia-smi` не являются универсальными командами любого Unix.

## 20. Как соотносятся API, ABI и POSIX

**API** — программный интерфейс на уровне исходного кода: названия функций, параметры и смысл операций. **ABI** — двоичный интерфейс, включающий соглашения о вызовах, раскладку данных и другие правила взаимодействия уже скомпилированного кода с системой. **POSIX** задаёт стандартизированные интерфейсы для переносимых Unix-подобных программ.

Например, библиотека может предоставлять POSIX-подобную функцию `read`, которая через ABI обращается к системному вызову Linux. Но не вся Linux-специфичная функция входит в POSIX. `epoll`, `cgroups` и namespaces — важные примеры Linux-механизмов, на которые переносимый POSIX-код не может автоматически рассчитывать.

Это полезно для понимания ошибок бинарных Python-зависимостей и нативных расширений. Совпадение языка программирования ещё не гарантирует совместимость архитектуры, системных библиотек и ABI.

## 21. Сборка всей картины на одном запросе

Предположим, на сервер приходит HTTP-запрос для детекции объектов.

1. Сетевой адаптер принимает кадр; драйвер и сетевой стек ядра обрабатывают данные.
2. Ядро связывает TCP-соединение со слушающим сокетом приложения.
3. Python/ASGI-сервер получает байты через системные интерфейсы, разбирает HTTP и вызывает обработчик.
4. Код загружает или использует модель: чтение весов прошло через файловую систему, page cache и драйвер накопителя.
5. PyTorch выделяет CPU/GPU-память и запускает вычисления; CPU-потоки планируются ядром, GPU-задачи обслуживаются драйвером и CUDA-инфраструктурой.
6. Приложение сериализует результат в HTTP-ответ; ядро отправляет байты через TCP и сетевой драйвер.

На каждом шаге ошибка выглядит по-разному: `Permission denied` при чтении модели, `CUDA driver version is insufficient` при проблемах совместимости GPU, `Address already in use` при занятом порту, `HTTP 500` при ошибке Python-обработчика. Разбираться в таком сервере легче, если знаешь, кто именно отвечает за каждое звено.

## 22. Диагностические команды как ответы на вопросы

| Вопрос | Наблюдение | Чего оно не доказывает |

| Какой дистрибутив представлен в userspace? | `cat /etc/os-release` | Конфигурацию ядра |

**Не срезай углы на трёх местах:** (1) не называй Ubuntu ядром; (2) не приписывай Bash ответственность за планирование процессов; (3) не утверждай, что контейнер несёт собственное Linux-ядро.

### Вопросы, которые стоит разобрать без подсказок

1. Что меняется после обновления Bash, а что после обновления ядра?
2. Почему Python может читать `/proc/meminfo` как файл, хотя это не обычные сохранённые данные на SSD?
3. Почему пользовательский Python не может напрямую обращаться к памяти ядра?
4. Как связаны `read()` в приложении, VFS и page cache?
5. Почему живой PID с открытым портом не гарантирует успешный inference?
6. Что общее у процессов в двух разных Docker-контейнерах на одной машине?
7. Почему в контейнере с Ubuntu `uname -r` может показать ядро Fedora-хоста?
