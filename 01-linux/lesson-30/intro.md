# 30. Автоматизация: cron, systemd timers, расписание

**Время:** ориентировочно 45–90 минут. Отдельные лабораторные создают отдельные Ubuntu VM.

## Кто запустит команду завтра

Интерактивный terminal не работает вечно. Для регулярной задачи нужны планировщик и сервисная среда. Традиционный `cron` использует записи формата `минута час день-месяца месяц день-недели команда`; например, `0 3 * * *` для запуска каждый день в 03:00 локального времени планировщика. Поведение при переводе часов и пропущенных запусках зависит от настроек и реализации.

## Что скрыто в cron

У задач cron обычно ограниченное окружение: PATH, рабочая директория и переменные могут отличаться от терминала. Отсюда частая история «вручную работает, а ночью падает». Используй абсолютные пути, явные переменные, журналирование и проверку статуса.

## Альтернатива: systemd timer

`systemd` поддерживает `.timer` units с календарным расписанием (`OnCalendar=`) либо относительными интервалами (`OnBootSec`, `OnUnitActiveSec` и др.). У таймера есть связанный `.service`, а журнал читается через journalctl. Полезно сначала освоить `systemd-analyze calendar`, который показывает, как systemd интерпретирует выражение, без создания реального таймера.

## Выбор подхода

Для одного разового скрипта cron может быть достаточен. Для сервиса с зависимостями, состояниями, логами и контролем запуска таймер systemd часто удобнее. В Kubernetes есть CronJob, в GitLab — scheduled pipelines. Принципы те же: расписание не гарантирует успешного выполнения.

**Не срезай углы:** не ставь фоновый cron, пока скрипт не умеет логировать ошибки и завершаться с осмысленным статусом. [systemd.timer](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html).
