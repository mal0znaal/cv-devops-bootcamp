# 08. Стандартные потоки: как программы соединяются между собой

Команда `echo hello` печатает слово в терминал. Команда `echo hello > message.txt` записывает его в файл. `echo` не должна уметь открывать `message.txt`, чтобы второй вариант сработал. Файл открывает Bash: он перенаправляет стандартный вывод команды. Это один из ключевых механизмов, на которых построены утилиты Unix.

## Откуда берутся stdin, stdout и stderr

Каждый обычный процесс начинает работу с набором открытых **файловых дескрипторов**. Дескриптор — небольшое целое число, через которое процесс обращается к открытому файловому объекту. По соглашению:

| Номер | Название | Назначение |
|---|---|---|
| 0 | stdin | Стандартный ввод |
| 1 | stdout | Стандартный вывод |
| 2 | stderr | Диагностические сообщения |

Если ты открыл интерактивную оболочку, эти дескрипторы обычно связаны с псевдотерминалом. Когда программа печатает байты в stdout, терминал показывает их на экране. Когда она ждёт stdin, ввод идёт от клавиатуры через терминальную сессию.

~~~bash
printf 'ordinary output\n'
printf 'error output\n' >&2
~~~

Обе строки будут видны в терминале, но идут по **разным дескрипторам**. Поэтому их можно по-разному направлять и обрабатывать.

## Где именно выполняется >

Запишем:

~~~bash
printf 'hello\n' > hello.txt
~~~

Bash разбирает командную строку, обнаруживает перенаправление и открывает файл на запись с усечением существующего содержимого. Затем stdout команды связывается с этим файловым объектом. `printf` получает обычный дескриптор 1 и пишет туда, не зная, связан он с терминалом или файлом.

Схема:

~~~text
без >:  printf ──stdout(1)──> терминал
с  >:  printf ──stdout(1)──> hello.txt
~~~

Если файл существовал, `>` обнуляет его до запуска команды. Даже неудачно запущенная программа способна оставить файл пустым после перенаправления. Это частая ошибка в скриптах, где файл одновременно используется как вход и выход одной команды.

`>>` меняет способ открытия: запись идёт **в конец**. Попробуй:

~~~bash
printf 'first\n' > ~/streams-demo.txt
printf 'second\n' >> ~/streams-demo.txt
cat ~/streams-demo.txt
printf 'third\n' > ~/streams-demo.txt
cat ~/streams-demo.txt
~~~

После последнего `>` в файле останется только третья строка. Никакого специального режима «перезаписи echo» не существует: всё произошло при открытии файла оболочкой.

## stdin и оператор <

`<` открывает файл для **чтения** и подключает его к дескриптору 0 процесса. Например:

~~~bash
wc -l < ~/streams-demo.txt
~~~

`wc` читает байты из stdin. Имя файла ему не передано, поэтому он сообщает только число. Сравни `wc -l ~/streams-demo.txt`: тут программа сама получает путь в аргументе и обычно выводит также имя файла.

Для некоторых утилит `-` в позиции имени файла означает «читать из stdin», но это соглашение программы, а не синтаксис ядра.

## Откуда появляется 2>

~~~bash
ls /no-such-directory > normal.txt 2> errors.txt
~~~

Обычные данные команды поступают в `normal.txt`, сообщения об ошибках — в `errors.txt`. Проверь оба файла через `ls -l` и `cat`. Здесь `2` указывает номер stderr.

Если нужно направить оба потока в один файл, используют:

~~~bash
ls /no-such-directory > combined.txt 2>&1
~~~

Оператор `2>&1` не означает «строка 2 больше строки 1». Он дублирует текущий дескриптор 1 как дескриптор 2. Bash выполняет перенаправления слева направо. Поэтому:

~~~bash
ls /no-such-directory 2>&1 > only-out.txt
~~~

**не эквивалентно** предыдущему примеру. Сначала stderr связывается с исходным stdout терминала, затем stdout перенаправляется в файл. Ошибка остаётся в терминале. Проверь оба варианта и объясни порядок операций.

## Что такое pipe

Символ `|` заставляет shell связать stdout одной команды со stdin другой. Например:

~~~bash
printf 'one\ntwo\nthree\n' | wc -l
~~~

Первая программа пишет в pipe, вторая читает из него. В файловой системе не создаётся промежуточный `temp.txt`. Оба процесса могут исполняться одновременно, а ядро буферизует данные pipe и при необходимости приостанавливает запись или чтение.

~~~text
printf --stdout--> [буфер pipe в ядре] --stdin--> wc
~~~

Сравни `printf ... > data.txt` и `printf ... | wc -l`. В первом случае получателем является файл, во втором — другой процесс. У двух форм разные задачи.

## Почему stderr по умолчанию не входит в pipeline

~~~bash
ls /missing | wc -l
~~~

`wc` считает строки **stdout** команды `ls`. Сообщение об ошибке остаётся в stderr и не попадает в `wc`. Для объединения потоков при необходимости используют `2>&1` либо Bash-оператор `|&`. Однако объединение ошибок и обычных данных иногда делает результат непригодным для автоматического разбора.

## Что такое tee

`tee` читает stdin, пишет копию в stdout и одну или несколько файловых целей:

~~~bash
printf 'model loaded\n' | tee ~/boot.log
~~~

Ты видишь сообщение и сохраняешь его. С `tee -a` текст добавляется, а без `-a` файл перезаписывается. `tee` часто встречается при логировании сборки и обучающих прогонов.

## Откуда ошибка sudo echo > protected-file

~~~bash
sudo echo hello > /root/output.txt
~~~

Здесь повышенные права получит `echo`, но попытку открыть `/root/output.txt` для перенаправления выполняет **твой обычный shell**. Поэтому команда может завершиться `Permission denied`. Один из вариантов для допустимых административных действий — `printf 'hello\n' | sudo tee /root/output.txt`: файл откроет `tee`, запущенная с нужными правами. В нашей практике писать в `/root` не требуется.

## Что происходит при завершении

У каждого процесса есть код выхода. В pipeline Bash без `pipefail` обычно возвращает код **последней команды**. Поэтому `grep nonexistent file | wc -l` способен вернуть статус ноль от `wc`, даже если `grep` не нашёл совпадений либо столкнулся с ошибкой. В уроке 29 разберём различие и способы безопасной обработки.

## Эксперимент: исследуй потоки

Выполни команды по очереди и сформулируй, где находятся байты после каждой:

~~~bash
printf 'a\n' > ~/a.txt
printf 'b\n' >> ~/a.txt
wc -l < ~/a.txt
cat ~/a.txt | grep b
ls /missing 2> ~/errors.txt
cat ~/errors.txt
~~~

Затем попробуй поменять `2>` на `>` и сравни. Не переходи к CHECK, пока не сможешь объяснить, кто открывает файл и чем отличается дескриптор 1 от 2.
