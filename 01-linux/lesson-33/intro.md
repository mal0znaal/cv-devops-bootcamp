# 33. Инцидент: процесс жив, но HTTP отдаёт 404

В этой лабораторной учебный `systemd`-сервис обслуживает статические файлы по HTTP. Процесс способен оставаться активным и слушать порт, даже если ему указан неверный каталог. Задача — отличить неисправность запуска от ошибки прикладной конфигурации.

## Что означает active

Для `Type=simple` systemd связывает состояние unit с жизненным циклом основного процесса согласно настройкам. Это не проверка файлов в `--directory` и не автоматический HTTP-запрос. Поэтому `active (running)` не означает, что приложение отдаёт нужную страницу.

## Почему возникает 404

Python `http.server` получает HTTP-запрос, сопоставляет URL с содержимым обслуживаемой директории и возвращает 404, если ресурс не найден. Если страница `index.html` находится в `/opt/cvbootcamp33/site`, а команда запуска указывает другой путь, процесс может быть исправен, но пользователь не получит страницу.

Сначала узнай фактическое поведение через `curl -i`. Затем найди параметры запуска в `systemctl cat cvbootcamp33.service` и сравни их с реальными каталогами. Это даст гипотезу, которую можно проверить.

## Какие команды отвечают на разные вопросы

`systemctl status` — менеджер видит живой процесс? `ss -ltnp` — сокет слушается на правильном адресе/порту? `curl -i` — какой результат выдаёт HTTP? `ls -la` — где лежат данные? `journalctl -u` — были ли ошибки запуска?

Не смешивай эти уровни: если curl получил 404, сетевое соединение состоялось; менять firewall для исправления отсутствующей страницы бессмысленно.

## Исправление минимальным изменением

Нужно изменить конфигурацию, отвечающую за расположение каталога, затем дать systemd перечитать unit и перезапустить сервис. Сравни ответ до и после. Окончательная проверка должна увидеть нужное содержимое страницы и отсутствие необходимости запускать процесс с привилегиями root.

## Что этот пример говорит об inference

Inference API может отвечать на запросы, но отдавать ошибку на `/predict` из-за отсутствия модели. Мониторинг процесса обнаружит только часть возможных отказов. Прикладной healthcheck должен проверять конкретные условия готовности.

**Не срезай углы:** не исправляй 404 заменой `User=nobody` на root или бессмысленным многократным restart. До изменения найди неверный путь в работающей конфигурации.

**Источники:** [Python http.server](https://docs.python.org/3/library/http.server.html), [systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html).

## Разбор ошибочной гипотезы

Инженер видит 404 и предлагает открыть порт в firewall. Но firewall обрабатывает сетевой трафик **до** прикладной обработки HTTP. Если `curl` уже получил 404 с заголовками Python `http.server`, это прямое доказательство, что соединение состоялось и запрос дошёл до HTTP-сервера.

Другая гипотеза — у пользователя `nobody` нет права читать каталог. Это возможно для некоторых конфигураций, но в учебном инциденте сначала сравни существование запрашиваемого `index.html` с параметром `--directory`. Если процесс обслуживает вообще другую директорию, повышение прав не адресует причину.

### Сформулируй критерий исправления заранее

Требуется не `systemctl status=active`, а одновременно: сервис запущен от `nobody`, HTTP 200, в теле `CV-SERVICE-READY`. Иначе ты можешь «исправить» запуск ценой потери принципа least privilege.

### Обновлённый unit ≠ обновлённый процесс

После редактирования unit нужен `daemon-reload`, затем `restart`. Служба получает новый аргумент каталога только при новом запуске. Повторный `curl` должен подтвердить, что приложение теперь читает нужные данные.
