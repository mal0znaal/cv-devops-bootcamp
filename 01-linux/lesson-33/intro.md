# 33. Практика: живой процесс, но сломанный HTTP

## Инцидент в сервисе компьютерного зрения

Представь, что на Linux-сервере лежит каталог с файлами для демонстрации ML inference-сервиса. После деплоя мониторинг сообщил: HTTP не отвечает ожидаемым содержимым. Соседний инженер говорит: «Да всё нормально, `systemctl` показывает active». Этой информации недостаточно.

**Что подготовлено:** в `/opt/cvbootcamp33` лежит сайт-заглушка (это не настоящая модель и не GPU-окружение); в `/etc/systemd/system/` есть unit `cvbootcamp33.service`, который должен обслуживать его по `127.0.0.1:8873`. Окружение намеренно испорчено. Нужно обнаружить причину, не получая готового ответа.

### План расследования

- `systemctl status cvbootcamp33.service` — жив ли менеджируемый процесс?
- `ss -ltnp` — слушает ли TCP-порт 8873?
- `curl -i http://127.0.0.1:8873/` — что возвращает HTTP?
- `journalctl -u cvbootcamp33.service -n 30 --no-pager` — есть ли ошибки?
- `systemctl cat cvbootcamp33.service` — что реально запускается?
- `ls -la /opt/cvbootcamp33` — доступны ли данные?

Это подсказки **по инструментам**, не готовое решение. Диагноз должен следовать из доказательств.

### Что особенно важно

У процесса может быть состояние active, порт может находиться в LISTEN, но **приложение всё равно не выполняет бизнес-функцию**. Это принципиальная разница между process check, readiness и прикладным healthcheck. В Docker и Kubernetes мы вернёмся к ней с liveness/readiness probes.

**Где нельзя срезать углы:** не пытайся лечить ситуацию `chmod 777`, `systemctl restart` и сменой порта одновременно. Запиши первую обоснованную гипотезу до изменений.
