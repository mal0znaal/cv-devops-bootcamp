# 03. Настоящий healthcheck

Создай исполняемый `~/lab34/health.sh`. Он должен выполнить `curl --fail --silent --show-error` (или эквивалент) для `http://127.0.0.1:8874/health` и завершаться с ненулевым кодом, если HTTP ошибочен. Вывод можешь подавить.

Запусти файл вручную и посмотри `echo $?`. Затем запиши в `~/lab34/runbook.md` минимум 200 символов объяснения: симптом → доказательства → причина → изменение → проверка.

**Не срезай угол:** healthcheck не должен просто возвращать успех. В реальном CI/CD ложный успех приводит к выкладке сломанного сервиса.

---

**CHECK** проверяет состояние, но не заменяет твой собственный разбор причин.

## Проверка должна падать, когда сервис недоступен

После написания `health.sh` проверь его при рабочем сервисе: ожидается код 0. Затем проведи **отдельный безопасный тест**: останови учебный unit, запусти `health.sh` и убедись, что он возвращает ненулевой статус. Верни сервис в рабочее состояние перед CHECK.

Если скрипт всегда сообщает успех, он не диагностирует ничего. Если проверка делает слишком дорогой запрос к GPU-модели каждую секунду, она способна мешать работе приложения. В этой лабораторной `/health` лёгкий и проверяет только наличие модели.

В `runbook.md` обязательно укажи первичный симптом, найденную причину, минимальное изменение и два результата проверки: здоровый и нездоровый.
