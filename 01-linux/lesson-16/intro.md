# 16. Права Linux: почему 644 работает для файла, а для каталога нужны другие биты

Права на файл и каталог устроены похожим образом, но биты означают разные операции. Это объясняет множество ошибок `Permission denied`, которые невозможно разумно исправить командой `chmod 777`.

## Как читать десять символов ls -l

~~~text
-rwxr-x---
~~~

Первый символ — тип: `-` для обычного файла, `d` для каталога, `l` для символической ссылки. Следующие девять символов делятся на три группы по три: владелец, группа, все остальные.

`r` — read, `w` — write, `x` — execute. Для обычного файла `r` разрешает читать содержимое, `w` — изменять, `x` — выполнять файл как программу (с учётом прочих условий). Эти биты проверяются относительно учётных данных процесса.

## Числовая запись

В каждой тройке `r=4`, `w=2`, `x=1`. Сумма определяет восьмеричную цифру: `7` означает `rwx`, `6` означает `rw-`, `5` — `r-x`, `0` — `---`.

`chmod 640 file` создаёт `rw-r-----`. `chmod 750 script.sh` создаёт `rwxr-x---`. В символической форме `chmod u+x file` добавит выполнение владельцу, не обязательно сбрасывая остальные биты.

## На каталоге x означает прохождение по пути

Для каталога `r` позволяет перечислить его имена, `x` — найти объект по известному имени и пройти по этому компоненту пути, `w` вместе с `x` — добавлять, удалять или переименовывать записи каталога.

Это значит, что файл может иметь режим 644, но пользователь не сумеет его прочитать по пути `/srv/models/model.pt`, если у него нет `x` на `/srv` или `/srv/models`. При разрешении пути ядро проверяет право поиска на **каждом промежуточном каталоге**.

### Контрастный эксперимент

~~~bash
mkdir -p ~/perm-lab/data
printf 'ok\n' > ~/perm-lab/data/info.txt
chmod 644 ~/perm-lab/data/info.txt
chmod 600 ~/perm-lab/data
ls ~/perm-lab/data
~~~

Когда у каталога нет `x`, даже доступный для чтения файл может быть недостижим по имени. Если ты работаешь как root в учебной VM, root может обходить многие проверки; поэтому для честного эксперимента используй непривилегированную учётную запись или внимательно изучи `path_resolution(7)`. После теста верни каталогу корректный режим.

## Удаление файла и родительский каталог

Удаление имени файла требует записи в **родительский каталог** и права поиска по нему, а не обязательно бита `w` самого файла. Дополнительные правила sticky bit и атрибуты файловой системы могут накладывать ограничения.

## Что делает umask

Когда программа создаёт файл, она запрашивает начальный режим. `umask` **снимает** определённые биты. Обычные начальные значения — 666 для файлов и 777 для каталогов. При umask 022 типичный новый файл получает 644, каталог — 755. Но нельзя выводить абсолютно все значения простым арифметическим вычитанием: здесь работают битовые операции и исходно запрошенный режим.

~~~bash
umask
umask -S
~~~

Не меняй глобальную umask без понимания последствий для всех новых файлов процесса.

## ACL и дополнительные механизмы

Обычные три тройки прав — не вся модель доступа. Существуют POSIX ACL, атрибуты файловой системы, sticky bit, setgid на каталогах, Linux capabilities, AppArmor/SELinux и правила mount. Поэтому `chmod 777` может не решить проблему и одновременно предоставить ненужные права.

## Как исследовать Permission denied

Проверь путь от корня до файла: `namei -l /path/to/file`, затем `stat`, `id` и группы пользователя, от которого работает процесс. При наличии ACL используй `getfacl`. Если файловая система смонтирована read-only, новые права не помогут — причина на другом уровне.

**Не срезай углы:** не применяй рекурсивный `chmod 777`. Если после нескольких осмысленных проверок проблема остаётся, ищи конкретный запрет, а не наращивай права.
