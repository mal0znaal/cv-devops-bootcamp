# 21. systemd: кто запускает службы, почему они падают и как их контролировать

Ручной запуск `python3 app.py` привязывает приложение к текущей пользовательской сессии и окружению. После перезагрузки машина не обязана автоматически запустить Python снова. На Ubuntu серверными службами обычно управляет **systemd** — процесс пользовательского пространства, запущенный как системный менеджер с PID 1.

## Что делает systemd

Systemd знает, какие службы нужно запустить, в каком порядке, с какими зависимостями и под какими пользователями. Он отслеживает состояние процессов, ведёт сведения об ошибках и предоставляет интерфейс `systemctl` для управления. Это не ядро и не замена Python. Systemd использует системные вызовы Linux и запускает обычные процессы, но организует их жизненный цикл.

## Что такое unit

Unit — объект конфигурации systemd. Самые знакомые виды: `.service` для служб, `.socket` для сокетов, `.timer` для расписаний, `.mount` для монтирований, `.target` для группировки зависимостей. Unit-файл описывает желаемое поведение.

Простейший сервис:

~~~ini
[Unit]
Description=Training HTTP server
After=network.target

[Service]
Type=simple
User=nobody
WorkingDirectory=/srv/cv-demo
ExecStart=/usr/bin/python3 -m http.server 8765 --bind 127.0.0.1
Restart=on-failure

[Install]
WantedBy=multi-user.target
~~~

`Description` — описание для людей. `After=` определяет порядок по отношению к другому unit, но **само по себе не обеспечивает его запуск**. Если нужно требовать наличие другого unit, используются другие зависимости, например `Requires=` или `Wants=`. Их сочетание с `After=` и различие между жёсткой и мягкой зависимостью нужно читать в `systemd.unit(5)`.

## Раздел Service

`Type=simple` сообщает менеджеру, как трактовать старт процесса; это не проверка HTTP-готовности. `User=nobody` задаёт учётную запись, `WorkingDirectory` — рабочий каталог, `ExecStart` — исполняемую команду и аргументы. `Restart=on-failure` задаёт условия перезапуска при ошибочном исходе, но не заменяет диагностику первопричины.

Особенно опасно воспринимать `ExecStart=` как полноценную строку Bash. Операторы `>`, `|` и `&&` там не исполняются автоматически как в терминале. Если нужна сложная логика, правильнее создать отдельный тестируемый скрипт или явно указать оболочку, понимая последствия.

## enable и start — разные операции

`systemctl start name.service` запускает службу **сейчас**. `systemctl enable name.service` создаёт конфигурационные связи, чтобы unit участвовал в соответствующем запуске при загрузке, когда это поддерживается настройками `[Install]`. Включённый unit может быть остановлен; запущенный unit может быть не включён на автозапуск.

~~~bash
systemctl status ssh.service
systemctl is-enabled ssh.service
systemctl is-active ssh.service
~~~

Названия служб зависят от установленной системы: например, `ssh.service` может отсутствовать в минимальной VM.

## Что делает daemon-reload

После изменения файла `/etc/systemd/system/name.service` менеджер должен перечитать определения unit: `systemctl daemon-reload`. Это **не** автоматический перезапуск самого приложения. Затем можно вызвать `restart`, `start` или другую нужную операцию.

## Почему active не значит healthy

Запущенный HTTP-сервер может честно возвращать 404, 500 или 503. Systemd видит работающий процесс, но не обязан знать, загрузилась ли модель YOLO и способен ли сервер выполнять inference. Для проверки прикладной готовности используется HTTP-healthcheck или специализированное наблюдение; это станет важным при Docker, Kubernetes и Prometheus.

## Разбор одной неисправности

Сервис вернул `Active: active (running)`, но `curl` показал HTTP 404. Проверь `systemctl cat service`, `WorkingDirectory` и аргументы `ExecStart`: возможно, веб-сервер обслуживает не тот каталог. Изменение `Restart=always` не исправит неверный путь. Перезапуск приложения с тем же ошибочным конфигом лишь повторит проблему.

## Эксперимент с документацией

Открой `systemctl --help`, затем [systemd.service(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html). Найди `Restart=`. Потом [systemd.exec(5)](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html) — `WorkingDirectory=` и `User=`. Не перепутай описание unit и условия запуска процесса.

**Не срезай углы:** не заменяй непривилегированного пользователя root только ради успешного старта. Измени путь или права, доказав первопричину.

**Источники:** [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html), [systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html), [systemd.unit](https://www.freedesktop.org/software/systemd/man/latest/systemd.unit.html).

## Что происходит между systemctl start и работающим Python

Команда `systemctl start cvbootcamp.service` отправляет запрос системному менеджеру. Systemd читает unit и организует запуск программы с заданными credentials, рабочей директорией и окружением. В результате появляется обычный процесс Python. Этот процесс не «живёт внутри systemd»: менеджер отслеживает его состояние и управляет жизненным циклом.

Для `Type=simple` сообщение об успешном запуске может относиться к факту создания процесса, а не к завершению инициализации приложения. Если модели YOLO нужно 20 секунд на загрузку, systemd не узнает автоматически, когда inference действительно готов. Отсюда необходимость отдельного прикладного healthcheck.

### Запуск от User=nobody и доступ к каталогу

`http.server` от непривилегированного пользователя читает обслуживаемые файлы. Директория `/tmp/lab21-site` должна быть доступна этому пользователю на поиск и чтение. Если `WorkingDirectory` указывает в недоступный каталог, запуск может завершиться ещё до выполнения Python-команды. Сравни диагностику из `systemctl status` и `journalctl` с правами через `stat`.

### Почему daemon-reload не исправляет процесс сам по себе

Unit — это конфигурация менеджера. `daemon-reload` перечитывает определения, но запущенный Python уже получил свои argv, cwd и environment при старте. Поэтому изменённый `ExecStart` требует перезапуска приложения. Представь это как изменение файла конфигурации без перезапуска программы, которая прочитала его только при старте.

### Исследование unit

~~~bash
systemctl cat cvbootcamp.service
systemctl show cvbootcamp.service -p ExecStart -p User -p WorkingDirectory
~~~

Первая команда показывает исходный текст и drop-in-фрагменты, вторая — фактические свойства, известные менеджеру. Если они различаются, выясни, какой unit и какие переопределения реально загружены.
