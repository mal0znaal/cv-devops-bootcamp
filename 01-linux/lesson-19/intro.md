# 19. CPU, RAM, load average: как понять, чем занят сервер

Фраза «сервер медленный» не содержит диагноза. Узкое место может быть в CPU, RAM, файловой системе, сетевом соединении, блокировке Python или видеопамяти. Разные инструменты измеряют разные величины, поэтому не надо смешивать их в один условный «процент нагрузки».

## CPU utilisation

`top` и `ps` дают сведения о процессах и потребляемом процессорном времени. Отображаемый процент CPU зависит от способа подсчёта, в том числе количества логических процессоров и режима утилиты. Процесс с несколькими рабочими потоками может занимать больше одного логического ядра.

~~~bash
nproc
top
ps -eo pid,comm,%cpu,%mem --sort=-%cpu | head
~~~

Сначала установи число CPU и тип нагрузки, затем делай выводы.

## Load average

`uptime` показывает среднее количество задач, которые были runnable или находились в некоторых типах непрерываемого ожидания, на интервалах 1, 5 и 15 минут. Это не процент занятости CPU. Высокий load average может появляться при заторможенном I/O, даже если CPU не загружен на 100%.

## Что означает free -h

Linux использует оперативную память под page cache и другие кэши. Поэтому показатель `free` бывает маленьким даже на здоровой системе. `available` оценивает память, которую можно выделить новым программам без интенсивного вытеснения в swap. Он не является абсолютной гарантией: крупные аллокации и текущая конкуренция за память могут изменить ситуацию.

~~~bash
free -h
grep -E 'MemTotal|MemFree|MemAvailable|Cached|Swap' /proc/meminfo
~~~

## Несколько названий, встречающихся в диагностике памяти

**RSS (Resident Set Size)** — приблизительная оценка страниц памяти процесса, находящихся в RAM; она не равна сумме всех выделений Python и может включать разделяемые страницы. **VRAM** — память графического ускорителя; её потребление следует измерять средствами GPU. **OOM (out of memory)** — ситуация нехватки памяти; `OOM killer` — механизм ядра, который в определённых условиях выбирает процесс для принудительного завершения. **Swap** — область для вытеснения части страниц из RAM, обычно на накопитель, с существенными отличиями по скорости.

## OOM и память Python

Когда памяти не хватает, ядро может задействовать swap, замедляя работу, а при критической нехватке применить OOM killer. В журнале можно искать признаки завершения процесса из-за OOM. Не всякое падение Python из-за MemoryError означает именно OOM killer: ошибка выделения памяти в приложении и принудительное завершение процесса — разные сценарии.

## GPU — отдельные счётчики

Для обучения YOLO RAM даталоадеров, page cache, CUDA VRAM и GPU compute измеряются отдельно. `free -h` не говорит, сколько VRAM доступно, а `nvidia-smi` не показывает всё потребление системной памяти.

**Не срезай углы:** прежде чем перезапускать «жирный» процесс, запиши симптомы, фактические значения и гипотезу. Изучай [proc(5)](https://man7.org/linux/man-pages/man5/proc.5.html).

## Конкретная диагностика нагрузки ML-приложения

Представь, что обучение идёт медленно. `top` показывает один поток Python на 100%, `nvidia-smi` при наличии GPU показывает загрузку ускорителя 10%, а `free -h` — много доступной RAM. Это повод исследовать подготовку батчей, декодирование изображений и число DataLoader workers, а не объявлять проблему нехваткой оперативной памяти.

В другом случае CPU почти свободен, но load average высок: часть задач может ждать дискового I/O. Тогда нужны инструменты наблюдения за I/O и состояниями процессов, а не случайное увеличение числа потоков.

### Различай кэш и утечку памяти

Page cache растёт, когда программа читает датасет. Он ускоряет повторный доступ и может быть перераспределён. Если процесс увеличивает собственную RSS и память не освобождается, расследование другое: смотри метрики процесса, историю аллокаций и жизненный цикл объектов Python.

### Счётчик во времени полезнее одного снимка

Разовый `top` покажет состояние в момент измерения. Нагрузка может быть периодической: например, GPU ждёт следующий batch при медленной подготовке данных. Для диагностики нужна последовательность значений и контекст запуска, а затем уже Prometheus/Grafana для постоянного наблюдения.
