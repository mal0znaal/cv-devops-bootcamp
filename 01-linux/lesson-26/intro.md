# 26. SSH: как клиент узнаёт сервер и зачем нужны два вида ключей

SSH используется для защищённого подключения к удалённой системе. Он создаёт шифрованный канал, проверяет подлинность сервера и аутентифицирует пользователя. Два последних процесса часто путают, хотя они защищают от разных проблем.

## Проверка сервера

При первом подключении SSH-клиент получает публичный host key сервера и показывает его отпечаток. Подтвердить неизвестный отпечаток без внешней проверки — значит довериться тому, кто ответил на сетевой запрос. Клиент хранит информацию о доверенных серверах в `known_hosts` и предупреждает при неожиданном изменении ключа.

Поэтому `StrictHostKeyChecking=no` не является нормальным универсальным решением ошибки проверки host key. Он устраняет один из механизмов защиты от подмены сервера.

## Аутентификация пользователя

Пара пользовательских ключей состоит из приватного и публичного. Приватный хранится у клиента и не передаётся на сервер как обычный пароль. Публичный добавляется в `authorized_keys` пользователя на сервере либо используется другой механизм регистрации доверенного ключа.

~~~bash
ssh-keygen -t ed25519 -f ~/ssh-training-key
~~~

Для реального ключа нужна подходящая парольная фраза. В одноразовой лабораторной допускается учебный ключ без неё, который не используется нигде ещё.

## Что находится в ~/.ssh/config

~~~sshconfig
Host cv-server
    HostName example.org
    User mluser
    Port 2222
    IdentityFile ~/.ssh/id_ed25519
~~~

`Host` — локальный псевдоним, остальные настройки сообщают клиенту, куда подключаться и какой ключ использовать. `ssh -G cv-server` выводит итоговую конфигурацию **без подключения**.

## Агент и проброс портов

`ssh-agent` хранит доступ к ключам для текущей сессии, уменьшая число запросов парольной фразы. SSH также умеет пересылать TCP-подключения через туннель. Например, локальный forwarding полезен для доступа к приватной Grafana на удалённом сервере, не публикуя её порт в интернет.

Но механизм портов необходимо понимать прежде, чем копировать параметры `-L`: в нём есть локальная точка прослушивания, удалённый адрес назначения и SSH-сервер.

## Что происходит при подключении

Клиент устанавливает TCP-соединение, согласует криптографические параметры, проверяет идентичность сервера, проходит аутентификацию пользователя и открывает сеанс либо канал удалённой команды. Ошибка на каждом этапе имеет свои симптомы.

**Не срезай углы:** приватный ключ не отправляют в чат, GitHub и логи; проверку серверного ключа не отключают без конкретного основания.

**Источники:** [OpenSSH Manual](https://www.openssh.com/manual.html), [ssh_config(5)](https://man7.org/linux/man-pages/man5/ssh_config.5.html), [MIT Missing Semester — Remote Machines](https://missing.csail.mit.edu/2026/command-line-environment/).

## Как отличается проверка host key от пользовательского ключа

Представь поддельный сервер, ответивший на DNS-имя настоящего. Пользовательский приватный ключ не обязан утечь при корректном протоколе, но ты всё равно можешь отправить данные и команды не туда. **Host key** помогает убедиться, что соединение устанавливается с ожидаемым сервером. Пользовательская ключевая пара, напротив, нужна для проверки права **клиента** войти в учётную запись.

### Почему приватный ключ нельзя хранить в репозитории

Приватный ключ позволяет проходить аутентификацию от имени пользователя в пределах предоставленного доступа. Даже если ключ защищён парольной фразой, его публикация расширяет поверхность атаки. В GitLab CI лучше использовать отдельные deploy-credentials с минимальными полномочиями, а не рабочий личный ключ.

### SSH config — часть диагностики

`ssh -G cv-server` показывает итоговые параметры без сетевого соединения. Это помогает выяснить, почему клиент идёт на порт 22 вместо 2222 или выбирает не тот ключ. `ssh -v` и `ssh -vv` включают диагностический вывод подключения, но публиковать его следует после просмотра на предмет конфиденциальных данных.

### Туннель к Grafana

Локальный forwarding направляет подключение к локальному порту через SSH-сервер на разрешённый адрес назначения. Это может дать доступ к внутренней Grafana без публикации её HTTP-порта наружу. Но безопасность туннеля определяется тем, кто имеет SSH-доступ и куда настроено перенаправление.
